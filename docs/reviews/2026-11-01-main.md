## Summary
This change adds an authenticated mock payment transition and updates the checkout and receipt flow to distinguish pending from paid orders. The transition is atomically scoped to the order, owner, and pending status, and the client does not supply a payment amount. The retry and non-pending branches currently roll back after loading an ORM object, which expires it before the code reads it; those requests can fail with an async lazy-load error instead of returning the specified response. Tests use mocked session behavior and do not exercise this ORM expiration.

## Major
### 🟠 Loaded order is expired before retry/status handling, `backend-fastapi/app/services/order_service.py:218`
**Problem**: When the conditional update changes no row, the service loads `existing_order` and its items, then calls `db.rollback()` before reading `existing_order.status` or validating it into `OrderRead`. SQLAlchemy expires ORM state on rollback, including when `expire_on_commit=False`; accessing those expired attributes through an `AsyncSession` attempts implicit async I/O from ordinary attribute access.
**Why it matters**: The required idempotent retry for an already-paid order and the 409 response for an owned cancelled order can raise `MissingGreenlet`/an equivalent async lazy-load error and return a 500. This breaks AC-3 and AC-4 on these paths.
**Suggested fix**: Avoid rolling back the read-only transaction before converting the loaded order, or capture the needed data before rollback / re-query after rollback. Add coverage that exercises this branch with a real async SQLAlchemy session so expiration behavior is represented.

## Strengths
- The state transition uses one conditional `UPDATE` with ownership and pending-state predicates, so concurrent requests cannot independently transition the same pending order.
- The pay endpoint accepts no body, keeping amount and order data on the server.
